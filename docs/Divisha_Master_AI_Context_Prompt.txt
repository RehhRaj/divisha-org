## 3. NON-NEGOTIABLE ARCHITECTURAL PRINCIPLES

All architecture and implementation decisions must follow these principles.

1. **Business OS First.** Design reusable business capabilities for Divisha.org. The Dynamic Website Engine is the first commercial use of that foundation.
2. **Platform Before Product.** Build the shared tenant, authorization and metadata services required by the current product milestone. Grow the platform as later products need it.
3. **Kernel-Based Architecture.** The Kernel controls the request pipeline, context resolution, authorization, policy enforcement, execution, auditing, observability and rate limiting. Keep industry-specific rules in their owning modules.
4. **Capability-Based Authorization.** The platform owns capability definitions. Each tenant owns its roles, role-to-capability mappings and user-to-role mappings. Resolve permissions from capabilities and enforce them centrally through the Kernel.
5. **Metadata-Driven Architecture.** Use database metadata for configurable entity definitions, attributes, relationships, forms, workflows, business rules, UI definitions, website templates, navigation and pages. Use static code for generic engines and platform invariants. A vertical composed from existing runtime capabilities must be configurable without backend code changes, schema migrations or deployments. Additions to the underlying engine or its supported primitives are core platform changes and follow the ADR process.
6. **Multi-Tenant Isolation.** Tenant is the primary isolation boundary. Business type classifies a tenant and organizations represent units within a tenant. Resolve and validate the tenant before executing tenant-scoped work. Scope every tenant-owned resource to its tenant.
7. **Strict Layer Separation.** Follow the layer responsibilities in Section 4. Next.js renders and collects input. Django owns trusted tenant resolution, authorization, validation and business execution.
8. **Authentication ≠ Authorization.** Authentication establishes identity. Authorization evaluates whether that identity may perform the requested action in the resolved tenant. Public website reads use an explicit public-access policy for published resources.
9. **Immutable Request Context.** Create the context after resolving trusted request inputs and validating tenant status. Keep the resolved tenant and actor fixed during execution.
10. **Applications Cannot Bypass Kernel.** Route protected operations from APIs, admin actions, background jobs and AI through the same Kernel policy enforcement before execution.
11. **Contracts Before Implementation.** Define interfaces, payloads, errors and ownership boundaries before writing implementations.
12. **Registry Before Persistence.** Define or register supported templates, capabilities and schemas before saving records that reference them. The platform registry may expose code-defined primitives and registered database metadata. The domain registry maps hostnames to tenants from database records.
13. **Validation Before Persistence.** Validate input shape, metadata references, tenant ownership and business rules before committing writes. Use database constraints for invariants that must hold across concurrent requests.
14. **Tenant Isolation Must Be Verifiable.** Test tenant-scoped queries, caches and file access as each surface is introduced. Verify that Jeetu staff cannot access a Teal bill even by supplying its exact ID. For the first website milestone, verify isolation with protected tenant configuration.
15. **One Source of Truth per Record.** Store tenants, domains, business types and tenant configuration in the database. Give each configurable record one authoritative owner. If legacy sample tenants are retained, import them once and serve them from the database. Avoid runtime fallback to hardcoded tenant records.
16. **Deny by Default and Least Privilege.** Grant only the capabilities needed for the role. Authorize both the capability and tenant scope before execution. Keep actions such as `bill.create`, `bill.void` and `refund.issue` independently grantable when billing is introduced.
17. **Observable and Auditable by Design.** Correlate Next.js and Django logs with a request ID. Record the actor, tenant, action, target, timestamp and result for sensitive operations such as permission changes, bill voids and refunds. Keep secrets out of logs and audit records.
18. **Explicit State Transitions and Safe Retries.** Define allowed order and billing state transitions. When introducing retriable writes, make duplicate submissions safe across concurrent attempts. For example, retrying the same bill creation operation must produce a single bill.
19. **Evolve Contracts and Data Safely.** Plan API and schema changes for independently deployed frontend and backend versions. For a field rename, add the new field, migrate clients and data, then retire the old field when its consumers are ready.
20. **Separate Tenant Configuration from Secrets.** Store template choices, themes and settings such as `pos_enabled` in tenant configuration. Keep Django secret keys and provider credentials in appropriate secret storage. Use shared deployment settings for environment-level controls.
21. **Prove Recovery Before Going Live.** Before onboarding the first real client, restore a database backup into an isolated environment and verify tenant domains, settings and access controls.
22. **Keep the Core Modular and Deploy It Together.** Keep the Kernel, platform services, website publishing and future POS or billing in a modular Django backend with explicit boundaries. Introduce infrastructure and services when an approved phase needs them.

Authentication and authorization flow:

Identity resolution → Tenant context → Tenant role resolution → Capability resolution → Authorization decision → Execution

## 4. ARCHITECTURAL LAYERS

Maintain strict separation between:

1. Frontend Layer
2. API / Interface Layer
3. Kernel Layer
4. Platform Services Layer
5. Runtime Engine Layer
6. Metadata / Registry Layer
7. Persistence Layer
8. Infrastructure Layer

### Kernel

Controls execution and security.

### Platform Services

Provides reusable platform capabilities such as:

- Identity
- Tenants
- Metadata
- Policies
- Assets
- Events
- Search
- AI
- Subscriptions
- Vertical Registry

### Runtime Engines

Provides generic execution capabilities:

- Schema Engine
- Entity Engine
- Query Engine
- Website Engine

Do not place industry-specific business logic inside generic Kernel components.

## 6. COMMERCIAL PRODUCT STRATEGY

Initial commercial direction:

BASE BUSINESS OS + DYNAMIC WEBSITE ENGINE

Start with simple website products powered by the generic platform.

Initial examples:

- School Website
- Housing Society Website
- Tour & Travel Website

Each business type may have its own template and product configuration, but the underlying platform must remain generic.

Expected administration flow:

1. Platform Admin creates Tenant.
2. Admin selects Business Type.
3. Admin selects Website Template.
4. Admin enters business content and data.
5. System generates a preview.
6. Admin connects a domain.
7. Website is published.

All published websites and pages must ultimately be metadata/database-driven.

Use sample data for the rebuild and load it through the normal database-backed configuration path.

### First rebuild milestone

Use Django Admin to configure one sample tenant, its business type, hostname and template in PostgreSQL. Resolve that hostname in Django and render the right published site in Next.js. Add request ID correlation and verify that a user scoped to one tenant cannot read or edit another tenant's protected configuration. An isolation test may create a second tenant as a test fixture. Add audit events and retry protection with the operations that need them. Complete the restore test before onboarding real client data.

## 7. DOMAIN AND TENANT RESOLUTION

Domain resolution must follow this general flow:

Incoming Hostname
→ Domain Registry Lookup
→ Tenant Resolution
→ Tenant Status Validation
→ Context Creation
→ Public-access policy or capability check
→ Runtime Execution
→ Response

Tenant status must be validated.

Examples:
- ACTIVE
- SUSPENDED

Business Types must be configurable through database records rather than hardcoded Django choices.

## 10. SECURITY AND QUALITY REQUIREMENTS

Security must be designed into the platform, not added later.

Preserve:

- Strict tenant isolation
- Centralized authorization
- Capability-based permissions
- Immutable request context
- Input validation
- Secure domain resolution
- Audit trails
- API security
- Protection against unauthorized cross-tenant access

Do not trust frontend authorization alone.

All sensitive operations must be validated by the backend.
